# GoTry Repository Agent Contract

- Upstream documents take precedence: the technical authority is `docs/architecture.md` (system/ADR/evolution/debt); program-level decisions live in `docs/gotry-master-outline.md` (the master outline); the reuse matrix (§2) is a hard constraint — code-level adoption is limited to open-source imports; internal assets are bridge/reference only.
- **Every agent/tick entering this repo first sweeps async work orders**: if `ts/gotry-state/async/` contains a `*.json` without a same-named `.deliverable.md`, run `cd ts && npx tsx scripts/async-collect.ts <工单id>` (the "come back in an hour" scheduling loop is driven by this rule).
- Layering discipline: arithmetic lives only in the evaluate layer of `model.ts`/`unified.py`; solving lives only in `unified.ts`/`unified.py`; engine.*/journey.* are deprecated compatibility layers — new code must not call them. Changing either side requires running the full-stack regression (`scripts/run-all-tests.sh`; Python 20/20 + all TS suites green).
- No TS↔Python bridge: py/gotry_feasibility serves only as a historical comparison oracle, with zero references from the product runtime and toolchain; no new Python dependency surface may be added.
- dsh tracks main (founder decision): after upgrading, first run `cd ts && npx tsc --noEmit && npx tsx scripts/smoke.ts`.
- Documentation discipline: one file carries one concern; version history belongs to git — no vN suffixes; GoTry documents all live in this repo; directory taxonomy/naming/header blocks/lifecycle/readability discipline and the master index are in `docs/README.md`. **Bilingual discipline (founder decision 2026-09-10, loopx convention)**: every document is maintained as a pair — English base `x.md` + Chinese mirror `x.zh-CN.md` (machine-generated `CHANGELOG.md` exempt); editing either side requires syncing the other in the same commit, and **divergence between the pair is a bug**; `node scripts/check-docs-i18n.mjs` is the mechanical check, wired into the `run-all-tests.sh` regression gate.
- State-sync discipline: any commit that changes the system's current shape/state/debt must synchronize all state surfaces listed in `architecture.md` §11 (6 places) in the same commit; M-exit commits attach the freshness-checklist reconciliation results in the commit message.
- Red lines in code: a motivation profile without evidence is refused persistence; wish pool entries mandate conditions; write operations (booking/payment tools) must go through WriteGate in the future (no direct write may be implemented before confirmation exists).
- Before committing, run `git status --short` and be able to explain every entry; **stage only the specific files you own — `git add -A`/`git commit -am` sweeping the worktree is forbidden** — when multiple agents work in parallel the worktree often mixes in others' work in progress; the commit message states the "why" in one sentence; no merging with red tests.
- Release discipline (changed to a confirmation system by the founder on 2026-08-28): **whether to release and which version is confirmed by the founder; after confirmation, tagging / pushing the remote / npm publishing / release notes are done by the executing agent — the owner need not do it personally**. npm publish and dist-tag writes are protected by account-level 2FA — **the standard action = one browser approve at publish time, clicked by the founder** (bypass-2FA tokens are being tightened by npm; details in `docs/tokens.md`); dist-tag maintenance (rc tag migration/deprecate/stray cleanup) is done in passing within the same authorization window (#50③). The publish command must pass dist-tag explicitly (`TAG=latest ./scripts/publish-npm.sh`, #50①). Before releasing, the release gate must pass — ① full-stack regression green ② the six state surfaces of `architecture.md` §11 synchronized ③ every README usage item actually tested (the npm form must really install and really run plugin loading — a web 200 does not count) ④ License clear ⑤ the version number consistent across the tag and all docs; after publishing, a pull-back verification from the registry is mandatory (`npm view dist-tags` + a clean install) — **without the pull-back, no state surface may say "published"** (the rc.16 lesson: the tag was pushed and docs claimed published, but the registry actually had no such version; #50 erratum). No release without founder confirmation; no claiming "published" without passing the gate.

- **CHANGELOG mechanism (owner addendum 2026-08-30)**: `ts/scripts/build-changelog.ts` + `CHANGELOG.md` are the machine authority for version changes (Keep a Changelog 1.1.0 + Conventional Commits parsing); `docs/release-notes.md` is the human-written decision surface (founder/gate surface); the two coexist — the CHANGELOG is auto-derived from the commit log, while release-notes carry the human-written "why" (ADR-19-class decision surface); the `scripts/publish-npm.sh` gate includes build-changelog + git validation, and after a successful publish it automatically runs `gh release create` to create the GitHub Release (notes assembled from the same sections of CHANGELOG + release-notes).

## State Discipline for Inspections/Tests

The dsh runtime state directory (`ts/dsh-runtime/gotry-state/`) is the founder's real
product data (motivation profile / wish pool). Inspection or test prompts **must not
write into shared state**:
- Only do read-only verification (reading files / doctor / side-effect-free tool calls);
- When a write path must be verified (motivation save / wish pool insertion), run the
  plugin with an isolated `stateRoot` (the way smoke does it) — never run write-type
  test prompts directly via `./gotry`;
- Historical lesson: on 2026-08-26 an inspection used a real session to write into the
  wish pool / rewrite the motivation profile, polluting the founder's data (all 4 wish
  pool entries came from tests).
