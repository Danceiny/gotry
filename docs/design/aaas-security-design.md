# AaaS Security Design: Threat Model (Draft)

> Role: the threat model of the multi-user GoTry service — assets, actors, trust boundaries, threats, and the control and proving phase for each threat.
> Status: living (A0 of [#674](https://github.com/Danceiny/gotry/issues/674), drafted 2026-10-26; the [AaaS RFC](../rfc/aaas-rfc.md) was accepted 2026-10-28). A threat moves from proposed control to mitigated only when its falsification test passes.
> Upstream: [AaaS RFC](../rfc/aaas-rfc.md); [architecture](../architecture.md) §1.3 invariants and ADR-23; hotel-be deployment constraints C2, C10, C13, C15 and C16.
> Downstream: the A2 adversarial suite, the A3 boundary ADR and failure drills, and the maintainers of the [security policy](../ops/security.md).
> Evidence boundary: this draft is analysis, not proof. A threat counts as mitigated only when its falsification test exists and passes. Drills and fixtures prove engineering behavior only.

## TL;DR

- The highest-impact threats are cross-tenant access (S-1 to S-4), cross-organization bridge routing onto another organization's supplier login (S-5), stale-owner writes (S-6), and bearer keys once traffic leaves loopback (S-7, S-8).
- Two invariants carry most of the weight: the tenant is derived only at the trusted seam, and every durable write is fenced by epoch.
- Today's per-node form is protected mainly by the loopback boundary (C2, C16) and ADR-23 request bindings. AaaS removes the loopback premise, so A2 and A3 must replace it.
- Supplier login state stays out of the cloud. AaaS adds no server-side session store.
- Denial of service is mostly about cost: LLM budget, planner workers, bridge long polls, and the organization's shared supplier login. It is also about the replica itself: one runaway planner child must not take the CPU, memory or file descriptors of every tenant on it (S-17).
- Execution isolation is narrow in v1, because the planner can run no code. What the tenants of a replica still share (CPU, memory, descriptors, the LLM credential, the provider's prompt cache, the executor's host browser) has one control each, S-16 to S-19. The entry criteria for what is not built are in RFC §4.8.

## 1. Scope and assets

| Asset | Where it lives | Why it matters |
|---|---|---|
| Tenant ledger | Motivation, wish pool, companions, timeline, Booking Copilot tasks, work orders | Personal data; companion constraints may include health and diet |
| Tenant working files | The planner working directory, handoff tickets, deliverables, artifacts | Same sensitivity as the ledger |
| Organization bridge lane | `bridge.db` and the extension long poll | Routes jobs onto a real supplier login held in an employee browser |
| Service credentials | One BFF bearer key per surface (C13); LLM provider keys | Impersonation and spend |
| Budgets | LLM tokens, planner workers, supplier pacing | Cost and the organization's standing with suppliers |
| Off-node copies | Replicated tenant files and snapshots | Deleted data could survive here |

## 2. Actors and trust boundaries

| Actor | Trust | Notes |
|---|---|---|
| End user (tenant) | Authenticated by the organization's BFF | May be curious about, or hostile to, other tenants |
| Organization BFF | Trusted to authenticate users and assert the principal | With per-organization credentials, a compromised BFF can impersonate only its own organization's users |
| Browser extension | An untrusted transport inside an employee browser | Holds the supplier login; authenticated by organization-scoped join tickets that hotel-be issues (C16) |
| Content sources | Untrusted | Supplier pages, web results and model output are data, never instructions |
| Intranet peer | Untrusted | Relevant once the tier leaves loopback (A3) |

The trust boundaries are: browser to BFF (hotel-be is the authority); BFF to the gotry tier (loopback today, intranet at A3); replica to the lease store and the object store; and tenant to tenant inside one replica.

## 3. Threats

| ID | Threat | Today | Proposed control | Proving phase and falsification test |
|---|---|---|---|---|
| S-1 | A request supplies or alters a tenant id to read another tenant's state | Server paths share tenant `local`; ADR-23 binds principal and scope digests | Seam-only derivation (`HMAC(K_org, issuer ‖ subject)`); no quota or surface API accepts a tenant id (the router's `openTenant`, `handleOf` and `tenantRootOf` take format-checked strings, so "seam only" holds by call site, not by type) | A2: forged tenant fields in the body, headers, tool arguments and model output are ignored or rejected **Mitigated in A2** (run-all §94 A1–A6 and E1): the tenant comes only from the authenticated caller; a body, header, tool argument or model output that names one changes nothing. |
| S-2 | Shared state leaks across tenants through a shared ledger, cache, planner session or working directory | One `local` ledger per node | One ledger and one working directory per tenant; planner sessions and caches keyed by tenant | A2: two tenants with colliding task handles, request keys and wish names each read only their own rows **Mitigated in A2** (§94 B1–B3): colliding ids, decision flights and wish names stay per tenant. The planner's own working directory is per tenant through `TenantPlannerProvider`, proven with fakes only, not against a live dsh. |
| S-3 | An id becomes a path and escapes its directory | Ids are validated per surface | Tenant ids are fixed-format hex digests; paths are built only from them | A2: path-shaped and oversized ids are rejected before any filesystem call **Mitigated in A2** (§94 C1–C3, §93 R4). The exported copy API does not take a root from its caller on trust either: `forgetTenant` deletes only the directory laid out for exactly that tenant, the path that was checked and not the string that was passed, and a durable delete takes whole segments, so `acme/` cannot take `acme2/` (run-all §101 P1, P2, P4). |
| S-4 | Tenant B replays a handle of tenant A (`taskHandle`, `requestKey`, artifact id) | Handles are bound to principal and scope digests | Handles resolve only inside the caller's tenant ledger | A2: a foreign handle returns not-found, never another tenant's data **Mitigated in A2** (§94 D1–D4): a receipt for another tenant's task is a typed not-found, and a captured request replayed by another tenant becomes a fresh task in that tenant's own ledger. |
| S-5 | A bridge job of organization A runs on organization B's extension with B's supplier login, or B's result reaches A | No organization column; matching by site, origin and client id | An organization-scoped bridge ledger and owner; matching requires organization equality; organization-scoped join tickets | A2: cross-organization claims and result posts are rejected and leave no row **Mitigated in A2** (§95): organization equality in matching, results and pacing. The mounted production module stays single-organization (`local`) until A3 supplies organization-scoped credentials. The in-process pacing gate of the search is keyed by organization and site (§95 M7), and a module given an organization resolver refuses the cdp transport at construction (§95 M9). Limits: the bridge is one shared `bridge.db` with an `organization` column per node, not one file per organization; `admission` covers search and login/open only, so `/v1/session/status` and the extension endpoints are not metered, and every result for an unknown job id files an orphan row, so one organization can grow the shared ledger (A3); audit and verdict lines carry no organization; the migration of a legacy file is one way (roll back only while every row is `local`, otherwise restore a copy taken before the first start of the new binary). |
| S-6 | A stale owner keeps writing after a partition or a pause | One node, so not applicable | A lease with an epoch; epoch-scoped durable copies; a self-fencing margin; a drain with a deadline | A1: a paused owner's writes after takeover never appear in the restored ledger; a graceful handoff loses no acknowledged write (the ledger view closes when the final image is taken, the lease is renewed through the drain, and a flush that landed after the lease lapsed is reported as failed; a call that never returns cannot hold the lease for ever, because the drain gives up after `drainTimeoutMs` with a typed error and the tenant serves again) **Mitigated in the A1 follow-up** (run-all §101, after an independent review showed the first implementation let a write acknowledged after the final image be lost). |
| S-7 | A bearer key is sniffed or leaked once traffic leaves loopback | Loopback only (C2); one key per surface (C13) | Per-organization credentials, with mTLS or signed short-lived assertions | A3: the boundary ADR's tests reject unauthenticated and cross-organization calls |
| S-8 | Anyone holding the BFF key can assert any principal | Accepted while only the local BFF holds the key | Assertions signed per organization and bound to the request digest | A3: an assertion for organization B signed with A's key is rejected |
| S-9 | Supplier login state moves into the cloud | Red line: cookie values never cross the bridge protocol (extension tests §38) | AaaS adds no server-side session store; no schema carries a cookie value | A2: a schema scan finds no cookie-value field **Mitigated by convention in A2** (§94 H1, §95 S1): no schema has a cookie-value column and the protocol has no such field, but the bridge stores whatever JSON the extension posts, so a misbehaving extension could put a value into `result_json` or an event payload; an allowlist is A3. |
| S-10 | One tenant exhausts the LLM budget, planner workers, long-poll slots or ledger size | Request body limits; per-turn deadlines | Per-tenant and per-organization quotas; a global worker cap; typed 429 | A2: a flood from one tenant keeps another tenant's latency within budget **Mitigated in A2** (§93; §94 F4–F9). Counters are per replica, and LLM spend is charged at the configured worst case until the dsh adapter reports usage and whenever a feed reports nothing or zero tokens. Refusals by concurrency, rate and LLM budget come before a lease or a planner; a ledger-size refusal is decided once the tenant is open (its lease and restore have happened); a fresh tenant that is refused leaves no quota account; accounts idle for the longest window are swept together with their share of the organization's ledger total. |
| S-11 | One tenant gets the organization's shared supplier login rate-limited or banned | Pacing per node and per site | Pacing per organization and per site, with per-tenant shares | A2: a burst from one tenant is throttled before it reaches the site **Mitigated at organization scope in A2** (§95 pacing and admission hook, §93 R3). The per-tenant share of a site waits for A3's tenant-bearing bridge credential. The in-process pacing gate of the search is keyed by organization and site (§95 M7): one organization's call neither paces another nor shows when it last searched. |
| S-12 | Deleted data survives in off-node copies | No off-node copies exist yet | Forget deletes the tenant file and its off-node copies together | A1: after forget, no copy of the tenant can be restored; a snapshot upload under way when forget begins finishes first and is deleted with the rest, and none starts after (run-all §101). Forget keeps the lease renewed while it waits for that upload and wins against a handoff that is flushing (F3 to F6); it deletes only the epochs at or below the floor it raised, so a successor that took the tenant over meanwhile keeps what it wrote (F7). What a superseded owner uploaded after the forget is swept beside the next open of the tenant (S1, S2), or by `sweepMaskedCopies` run by an operator for a tenant that is never opened again. A replica that crashed or lost its lease keeps its local file until the next open of that tenant on it, whose restore replaces it; the file may hold writes that exist nowhere else, so an operator copies it first, and sweeping those files is for A3. Not covered: forgetting one subject inside a live tenant is not propagated into snapshots already published (immutable images, and a restore may fall back to an older verified one); A3 needs a retention policy and a rule against falling back across a forget. |
| S-13 | Prompt-injected content triggers cross-tenant reads or write actions | Observations are data; writes are sealed | Tools carry no tenant parameter; WriteGate unchanged | A2: injected instructions that name another tenant produce no cross-tenant read **Mitigated in A2** (§94 E1, with a positive control). |
| S-14 | A captured BFF request is replayed | Request keys are idempotent | Request keys scoped by tenant; assertion expiry | A2: a replay returns the original result and creates no new effect **Mitigated in A2** (§94 D3 and D4); assertion expiry is A3 (S-8). |
| S-15 | A mixed-version fleet enables a feature some replicas lack | Feature intersection rule (ADR-23) | Ownership moves only between compatible replicas | A3: a rolling-deploy drill keeps optional features off until every replica advertises them |
| S-16 | A provider's prompt cache lets one tenant infer whether another tenant's content was sent: both prompts share a cached prefix, and timing or the bill shows the hit | Every tenant's prompt shares one prefix up to the payload, and nothing fixes where tenant content begins | A per-tenant HMAC label (`pc-…`, under the organization key and its own context string) sits after the instructions every tenant shares and before any tenant-controlled or tenant-derived byte; a malformed label is refused; the shared form is byte-identical | A2: two tenants sending identical content share a prefix that ends inside the label and holds no payload byte, whatever is sent; the same tenant keeps its own prefix **Mitigated in A2** (run-all §98). Assumes the provider caches by prompt prefix; the operator's own bill is unchanged. |
| S-17 | One tenant's planner child exhausts the CPU, memory or file descriptors of a replica and takes every tenant on it down | Wall-clock turn deadlines, process-group cleanup and a global turn cap; nothing bounds a child's memory or CPU, or how many tenants a replica holds open | Each planner process tree runs under a V8 heap cap, a sampled tree RSS and CPU cap and a cap on an unterminated line; a tree over a ceiling is killed and its turn ends as a non-retryable `PLANNER_FAILED`, never rerun; a tree the sampler cannot see for ten ticks in a row counts as over a ceiling of its own kind; `maxOpenTenants` refuses a tenant over the cap before its lease or any file exists | A2: a worker that leaks off-heap memory, leaks in a grandchild, spins, exhausts its heap or writes a line that never ends is stopped, typed and reaped while a neighbour keeps answering **Mitigated in A2** (run-all §96). The sampler reads `ps` once a second; the defaults are unreviewed; there is no uid, cgroup or egress separation; a heap death in the runtime below the worker is not typed (the answer is the same, only the metric differs); where the process table cannot be read, or does not answer in five seconds, every real planner port refuses to start a child, and a sampler that goes blind later fails closed after ten ticks (a worker that reports a pid that is not its own is torn down with a typed reason). |
| S-18 | The deployment's LLM credential is read from a process that model output steers and is used elsewhere or for longer | The credential sits in the planner child's environment, valid from anywhere until rotated | A loopback broker holds the key and base URL; each planner process tree gets a ticket that works only against the broker, for a bounded number of requests and a bounded time, and dies with its port; revoking a ticket cancels what it has in flight; an upstream error body is never relayed, only its status, a closed code and kind and a numeric retry hint; the port the child holds caps connections and drops one that never starts a request; the real planner of the tenant form cannot be built without a broker; a ticket's measured usage is charged to its own tenant | A2: the child is given the ticket in place of the key and base URL, and the ambient `LLM_API_KEY` and `LLM_BASE_URL` are removed, checked against a real worker with an uncorrected control that does leak; a real dsh run through the broker yields its decision; the upstream sees the real key only from the broker; a ticket for another broker, a revoked, an expired or an exhausted one reaches nothing; an upstream that echoes the credential it was sent hands the child a mapped error without it; revoking a ticket breaks its open stream and cancels the upstream request; forty connections that say nothing, or never finish their headers, are cut to the cap and dropped **Mitigated in A2** (run-all §97). Narrows a compromised child, not a compromised gotry process; carries the chat-completions route only. |
| S-19 | A second organization's caller rides the executor's host browser and, with it, the first organization's supplier login | The executor module has one deployment key and drives one host Chrome | The module knows whose login the host browser holds and serves only that organization; the caller's organization is resolved by the host and never read from the request; a deployment that serves several organizations must name the owner; an injected observer is told the caller's organization | A2: a foreign organization is refused before the browser is touched; a body, header or query that names another organization changes nothing **Mitigated in A2** (run-all §99) for the host-browser executor. A multi-tenant cloud browser is not built (RFC §4.8 entry criteria). The session-search module's own cdp path is closed the same way: with an organization resolver the module refuses the cdp transport at construction (§95 M9). An injected `observe` skips the executor's check by contract. |

## 4. Security invariants

1. The tenant is derived at the trusted seam, from the authenticated principal, and nowhere else.
2. Every durable write carries its writer's epoch; a lower epoch never becomes authoritative.
3. A tenant's ledger, files, caches and planner sessions are reachable only through that tenant's handle.
4. Bridge jobs and results never cross an organization.
5. No supplier credential value exists on the server.
6. Forget removes a tenant from every copy, including off-node ones.
7. The gotry tier is never browser-reachable (C16).
8. Every planner process tree runs under resource ceilings; a tree over a ceiling is killed and its turn fails without a retry.
9. In the tenant form no planner process holds the upstream LLM credential; it holds a ticket that dies with its port.
10. Every tenant's planner prompt carries that tenant's cache partition label ahead of any tenant-derived byte.
11. The executor's host browser serves only the organization whose supplier login it holds.

## 5. Rejected options

| Option | Why it is rejected |
|---|---|
| Let the browser or the extension call the gotry tier directly | It puts the server key in the browser and makes gotry browser-reachable (C16) |
| Accept a tenant id from the BFF payload | Any payload bug becomes cross-tenant access; the seam derives the tenant instead |
| Rely on a Redis or database lock without fencing | A lost or duplicated lock would let two writers commit |
| Store supplier cookies on the server to share logins | It violates the 2026-09-11 decision and turns the service into a login farm |
| Design host- and storage-level access control now: file permissions, encryption at rest, operator audit | Access control lives at the presentation layer, where every read and write already resolves one tenant at the seam; ops-level redundancy waits for a real need (founder, 2026-10-26) |
| A microVM or gVisor sandbox per planner task in v1 | The v1 planner can run no code or command (plugins disabled, `toolBash` off), so a sandbox would isolate nothing it can reach. It becomes the baseline for the hosted conversational agent (Q6) and for any multi-tenant cloud browser; RFC §4.8 lists the entry criteria |
| Per-tenant provider API keys in place of a broker and a cache label | It needs the provider to offer it and gives a control that cannot be tested offline; the broker and the label are tested at our own boundary. Either can be added later without removing them |

## 6. Open questions

- Which signed-assertion format the BFF can issue (A3 boundary ADR).
- Whether the model provider isolates prompt caches per API key or workspace. That would make the cache label redundant, not harmful.
- The production values of the planner ceilings, `maxOpenTenants` and the global turn cap, after probes of the real nodes ([capacity baseline](../ops/aaas-capacity-baseline.md)).
