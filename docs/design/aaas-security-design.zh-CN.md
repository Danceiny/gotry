# AaaS 安全设计：威胁模型（初稿）

> 定位：多用户 GoTry 服务的威胁模型——资产、参与者、信任边界、威胁，以及每项威胁的控制措施与证明阶段。
> 状态：living（[#674](https://github.com/Danceiny/gotry/issues/674) 的 A0，2026-10-26 起草；[AaaS RFC](../rfc/aaas-rfc.zh-CN.md) 已于 2026-10-28 接受）。一项威胁只有在其证伪测试通过之后，才从「拟议控制」转为「已缓解」。
> 上游：[AaaS RFC](../rfc/aaas-rfc.zh-CN.md)；[architecture](../architecture.zh-CN.md) §1.3 不变量与 ADR-23；hotel-be 部署约束 C2、C10、C13、C15 与 C16。
> 下游：A2 对抗套件、A3 边界 ADR 与故障演练，以及 [安全策略](../ops/security.zh-CN.md) 的维护者。
> 证据边界：本稿是分析，不是证明。只有对应的证伪测试存在且通过，一项威胁才算已缓解。演练与夹具只证明工程行为。

## 速览

- 影响最大的威胁：跨租户访问（S-1 至 S-4）、跨组织桥路由落到另一组织的供应商登录态（S-5）、过期 owner 的写入（S-6），以及流量离开回环后的 bearer key（S-7、S-8）。
- 两条不变量承担了大部分防护：租户只在可信接缝处派生；每次持久写都按 epoch fencing。
- 现在按节点的形态主要靠回环边界（C2、C16）与 ADR-23 request binding 保护。AaaS 去掉了回环前提，所以 A2 与 A3 必须把它替换掉。
- 供应商登录态不进云。AaaS 不新增任何服务端会话存储。
- 拒绝服务主要是成本问题：LLM 预算、planner worker、桥长轮询，以及组织共用的供应商登录态。它也关乎副本本身：一个失控的 planner 子进程不能把其上每个租户的 CPU、内存或文件描述符一起拖走（S-17）。
- v1 里的执行隔离范围很窄，因为 planner 不能运行任何代码。同一副本上的租户仍共用的东西（CPU、内存、描述符、LLM 凭证、提供方的 prompt 缓存、executor 的宿主浏览器）各有一项控制措施，即 S-16 至 S-19。未建内容的入场条件见 RFC §4.8。

## 1. 范围与资产

| 资产 | 存放位置 | 为何重要 |
|---|---|---|
| 租户账本 | 动机、心愿池、同行人、时间线、Booking Copilot 任务、工单 | 个人数据；同行人约束可能包含健康与饮食信息 |
| 租户工作文件 | planner 工作目录、handoff 工单、交付物、artifact | 敏感度与账本相同 |
| 组织桥车道 | `bridge.db` 与扩展长轮询 | 把 job 路由到员工浏览器里真实的供应商登录态上 |
| 服务凭证 | 每个服务面一把 BFF bearer key（C13）；LLM 供应商密钥 | 冒充与花费 |
| 预算 | LLM token、planner worker、供应商节律 | 成本，以及组织在供应商处的信誉 |
| 异地副本 | 复制出的租户文件与快照 | 已删除的数据可能残留在这里 |

## 2. 参与者与信任边界

| 参与者 | 信任 | 说明 |
|---|---|---|
| 终端用户（租户） | 由组织的 BFF 认证 | 可能对其他租户好奇或怀有敌意 |
| 组织 BFF | 被信任去认证用户并断言 principal | 采用按组织的凭证后，被攻破的 BFF 只能冒充本组织的用户 |
| 浏览器扩展 | 员工浏览器内不可信的传输通道 | 持有供应商登录态；以 hotel-be 签发的组织作用域 join ticket 认证（C16） |
| 内容来源 | 不可信 | 供应商页面、网页结果与模型输出都是数据，绝非指令 |
| 内网对端 | 不可信 | 该层离开回环后（A3）才相关 |

信任边界：浏览器到 BFF（权威在 hotel-be）；BFF 到 gotry 层（现为回环，A3 起为内网）；副本到租约存储与对象存储；同一副本内租户与租户之间。

## 3. 威胁

| 编号 | 威胁 | 现状 | 拟议控制 | 证明阶段与证伪测试 |
|---|---|---|---|---|
| S-1 | 请求携带或篡改 tenant id，以读取其他租户的状态 | 服务端路径共享租户 `local`；ADR-23 绑定 principal 与 scope 摘要 | 只在接缝派生（`HMAC(K_org, issuer ‖ subject)`）；没有配额或服务面 API 接受 tenant id（router 的 `openTenant`、`handleOf`、`tenantRootOf` 接受经格式校验的字符串，所以「只在接缝」靠调用位置成立，而不是靠类型） | A2：请求体、header、工具参数与模型输出中伪造的租户字段一律被忽略或拒绝 **A2 已缓解**（run-all §94 A1–A6 与 E1）：租户只来自已认证的调用方；请求体、header、工具参数或模型输出中点名租户的内容不起任何作用。 |
| S-2 | 共享状态经共享账本、缓存、planner 会话或工作目录在租户间泄漏 | 每个节点一本 `local` 账本 | 每个租户一本账本、一个工作目录；planner 会话与缓存以租户为键 | A2：任务句柄、request key 与心愿名都相互碰撞的两个租户，各自只读到自己的行 **A2 已缓解**（§94 B1–B3）：相互碰撞的 id、决策 single-flight 与心愿名都按租户隔离。planner 自己的工作目录通过 `TenantPlannerProvider` 按租户划分，只用夹具证明过，未对真实 dsh 验证。 |
| S-3 | id 被当作路径并逃出其目录 | id 按服务面校验 | tenant id 是固定格式的十六进制摘要；路径只由它构造 | A2：形如路径与超长的 id 在任何文件系统调用之前被拒 **A2 已缓解**（§94 C1–C3、§93 R4）。 |
| S-4 | 租户 B 重放租户 A 的句柄（`taskHandle`、`requestKey`、artifact id） | 句柄绑定 principal 与 scope 摘要 | 句柄只在调用方自己的租户账本内解析 | A2：他人句柄返回 not-found，绝不返回其他租户的数据 **A2 已缓解**（§94 D1–D4）：针对他人任务的回执得到 typed not-found；被他人重放的截获请求，在该租户自己的账本里成为一个全新的任务。 |
| S-5 | 组织 A 的桥 job 在组织 B 的扩展上、用 B 的供应商登录态执行，或 B 的结果回到 A | 没有组织列；按站点、origin 与 client id 匹配 | 组织作用域的桥账本与 owner；匹配要求组织相同；组织作用域的 join ticket | A2：跨组织的领取与回包被拒，且不留任何行 **A2 已缓解**（§95）：匹配、回包与节律都要求组织相同。挂载的生产模块在 A3 提供按组织的凭证之前仍是单组织（`local`）。检索的进程内节律闸按组织和站点分键（§95 M7），配置了组织解析器的模块在构造时拒绝 cdp 传输（§95 M9）。局限：桥是每个节点一份共享的 `bridge.db`、带 `organization` 列，而不是每个组织一个文件；`admission` 只覆盖检索与 login/open，所以 `/v1/session/status` 与扩展端点不计量，每个针对未知 job id 的回包都会落一行孤儿行，一个组织因此可以撑大共享账本（A3）；审计与 verdict 日志行不带组织；旧文件的迁移是单向的（只有当所有行都是 `local` 时才能回滚，否则恢复首次启动新二进制之前做好的副本）。 |
| S-6 | 分区或停顿之后，过期 owner 继续写入 | 单节点，不适用 | 带 epoch 的租约；按 epoch 分区的持久副本；自我隔离 margin | A1：被暂停的 owner 在接管之后的写入，从不出现在恢复出的账本中；优雅交接不丢任何已确认的写入（取最终镜像时账本视图即关闭，排空期间租约持续续期，租约失效之后才落地的刷盘按失败报告）**已在 A1 后续修复中缓解**（run-all §101；一次独立审查指出，最初的实现会丢掉在最终镜像之后才确认的写入）。 |
| S-7 | 流量离开回环后 bearer key 被嗅探或泄漏 | 只走回环（C2）；每个服务面一把 key（C13） | 按组织的凭证，配 mTLS 或短时签名断言 | A3：边界 ADR 的测试拒绝未认证与跨组织的调用 |
| S-8 | 任何持有 BFF key 的人都能断言任意 principal | 只有本机 BFF 持有 key 时可以接受 | 按组织签名并绑定 request 摘要的断言 | A3：用 A 的密钥签发的组织 B 断言被拒 |
| S-9 | 供应商登录态进入云端 | 红线：cookie 值从不经过桥协议（扩展测试 §38） | AaaS 不新增服务端会话存储；任何 schema 都不携带 cookie 值 | A2：schema 扫描找不到 cookie 值字段 **A2 按约定缓解**（§94 H1、§95 S1）：没有任何 schema 有 cookie 值的列，协议里也没有这样的字段，但桥会原样存下扩展回传的 JSON，行为异常的扩展仍可能把值写进 `result_json` 或事件载荷；白名单留给 A3。 |
| S-10 | 单个租户耗尽 LLM 预算、planner worker、长轮询槽位或账本空间 | 请求体上限；每轮截止时间 | 按租户、按组织的配额；全局 worker 上限；typed 429 | A2：一个租户的洪峰下，另一个租户的延迟仍在预算内 **A2 已缓解**（§93；§94 F4–F9）。计数器按副本；在 dsh 适配器上报用量之前，以及任何数据源什么都不报或只报零 token 时，LLM 花费按配置的最坏情形计。并发、速率与 LLM 预算的拒绝发生在租约与 planner 之前；账本大小的拒绝在租户打开之后才判定（租约与恢复已经发生）；被拒的新租户不留配额账户；空闲超过最长窗口的账户会被清扫，连同它在组织账本总量里的份额。 |
| S-11 | 单个租户让组织共用的供应商登录态被限流或封禁 | 节律按节点、按站点 | 节律按组织、按站点，并按租户分配份额 | A2：一个租户的突发在到达站点之前即被限流 **A2 在组织层面已缓解**（§95 节律与准入钩子、§93 R3）。每租户在站点上的份额，等 A3 带租户身份的桥凭证。检索的进程内节律闸按组织和站点分键（§95 M7）：一个组织的调用既不给另一个组织定节律，也不暴露它上一次检索的时间。 |
| S-12 | 已删除的数据残留在异地副本中 | 尚无异地副本 | forget 同时删除租户文件及其异地副本 | A1：forget 之后，该租户的任何副本都无法再恢复；forget 开始时正在进行的快照上传会先完成并随其余副本一起被删除，此后不再有新的上传开始（run-all §101）。崩溃或丢失租约的副本会保留自己的本地文件，里面可能有仅存在于那里的写入；清扫它们是 A3 的运维步骤。 |
| S-13 | 被注入的内容触发跨租户读取或写动作 | 观测结果是数据；写路径封存 | 工具不带租户参数；WriteGate 不变 | A2：点名其他租户的注入指令不产生任何跨租户读取 **A2 已缓解**（§94 E1，带正对照）。 |
| S-14 | 截获的 BFF 请求被重放 | request key 幂等 | request key 按租户作用域；断言会过期 | A2：重放返回原结果，不产生新效果 **A2 已缓解**（§94 D3 与 D4）；断言过期归 A3（S-8）。 |
| S-15 | 版本混跑的集群启用了部分副本不具备的特性 | 特性交集规则（ADR-23） | 所有权只在兼容的副本之间移动 | A3：滚动发布演练中，直到全部副本都公告某可选特性之前，它保持关闭 |
| S-16 | 提供方的 prompt 缓存让一个租户推断出另一个租户的内容是否被发送过：两个提示共享缓存前缀，耗时或账单暴露了命中 | 每个租户的提示在载荷之前共用同一个前缀，且没有任何东西固定租户内容从哪里开始 | 每租户一个 HMAC 标签（`pc-…`，在组织密钥与独立的上下文字符串之下），位于各租户共用的指令之后、任何由租户控制或派生的字节之前；格式错误的标签被拒；共享形态逐字节不变 | A2：两个租户发送相同内容时，共享前缀止于标签之内且不含任何载荷字节，与所发内容无关；同一租户保有自己的前缀 **A2 已缓解**（run-all §98）。假设提供方按提示前缀缓存；运营方自己的账单不变。 |
| S-17 | 一个租户的 planner 子进程耗尽副本的 CPU、内存或文件描述符，把其上每个租户一起拖垮 | 只有挂钟轮次期限、进程组清理与全局轮次上限；没有任何东西限制子进程的内存或 CPU，也没有限制副本能同时持有多少租户 | 每棵 planner 进程树都在 V8 堆上限、按采样的整树 RSS 与 CPU 上限、以及对一直不换行的单行长度上限之下运行；越界的树被杀死，其轮次以不可重试的 `PLANNER_FAILED` 结束，绝不重跑；连续十次采样都看不到的树，按它自己的一类越界处理；`maxOpenTenants` 在取租约或建任何文件之前拒绝超过上限的租户 | A2：泄漏堆外内存、在孙进程里泄漏、空转、耗尽堆或写出永不换行的行的 worker，被停止、定型并回收，而邻居照常应答 **A2 已缓解**（run-all §96）。采样器每秒读一次 `ps`；默认值未经评审；没有 uid、cgroup 或出网隔离；worker 之下的运行时堆死亡没有类型（答复相同，只是指标不同）；进程表读不到或五秒内不应答时，每个真实的 planner 端口都拒绝启动子进程，而之后才失明的采样器在十次采样后失败即关闭（自报了不属于自己的 pid 的 worker 会被带类型地拆除）。 |
| S-18 | 部署的 LLM 凭证被一个由模型输出驱动的进程读到，并在别处使用或被用得更久 | 凭证放在 planner 子进程的环境里，在轮换之前从任何地方都有效 | 回环 broker 持有密钥与 base URL；每棵 planner 进程树拿到一张 ticket，它只对该 broker 有效，请求数与时间都有界，并随其端口失效；撤销 ticket 会取消它正在进行的请求；上游的错误体从不转发，只给状态码、封闭的错误码与类别和数字形式的重试提示；交给子进程的端口限制连接数，并丢弃一直不开始请求的连接；租户形态的真实 planner 没有 broker 就构造不出来；ticket 的实测用量记在它自己的租户头上 | A2：子进程拿到的是 ticket 而不是密钥与 base URL，且环境里的 `LLM_API_KEY` 与 `LLM_BASE_URL` 被移除，在真实 worker 上验证，并有不移除就会泄漏的对照；经 broker 的真实 dsh 运行能产出决策；上游只会看到来自 broker 的真实密钥；别的 broker 的、已撤销的、已过期的或已用尽的 ticket 什么也到不了；原样回显了所收到凭证的上游，交给子进程的是不含它的映射错误；撤销 ticket 会切断它已打开的流并取消上游请求；四十个什么也不说、或始终发不完 header 的连接被限制到上限并被丢弃 **A2 已缓解**（run-all §97）。收窄的是被攻破的子进程，不是被攻破的 gotry 进程；只承载 chat-completions 路线。 |
| S-19 | 第二个组织的调用方骑上 executor 的宿主浏览器，连同第一个组织的供应商登录态 | executor 模块只有一个部署密钥，驱动同一个宿主 Chrome | 模块知道宿主浏览器里是谁的登录态，只为该组织服务；调用方的组织由宿主解出，从不取自请求；服务多个组织的部署必须点名所有者；注入的观察器会被告知调用方的组织 | A2：别的组织在碰浏览器之前就被拒绝；点名另一个组织的请求体、header 或查询串毫无作用 **A2 已缓解**（run-all §99），针对宿主浏览器形态的 executor。多租户云端浏览器没有建（RFC §4.8 入场条件）。session-search 模块自己的 cdp 路径同样封住：配置了组织解析器时，模块在构造时拒绝 cdp 传输（§95 M9）。注入的 `observe` 按约定绕过 executor 的检查。 |

## 4. 安全不变量

1. 租户在可信接缝处、由已认证的 principal 派生，别处一律不派生。
2. 每次持久写都携带其写者的 epoch；更低的 epoch 永远不会成为权威。
3. 租户的账本、文件、缓存与 planner 会话只能经该租户的句柄触达。
4. 桥 job 与结果从不跨越组织。
5. 服务端不存在任何供应商凭证值。
6. forget 把租户从每一份副本中移除，包括异地副本。
7. gotry 层永远不被浏览器触达（C16）。
8. 每棵 planner 进程树都在资源上限之下运行；越界的树被杀死，其轮次失败而不重试。
9. 租户形态里没有任何 planner 进程持有上游 LLM 凭证；它们持有的是随端口失效的 ticket。
10. 每个租户的 planner 提示在任何由租户派生的字节之前，都带有该租户的缓存分区标签。
11. executor 的宿主浏览器只为持有该供应商登录态的组织服务。

## 5. 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 让浏览器或扩展直接调用 gotry 层 | 会把服务端密钥交给浏览器，并让 gotry 变成浏览器可达（C16） |
| 接受 BFF 载荷里的 tenant id | 任何载荷缺陷都会变成跨租户访问；租户改由接缝派生 |
| 依赖不带 fencing 的 Redis 或数据库锁 | 锁丢失或重复时会让两个写者都提交 |
| 在服务端保存供应商 cookie 以共享登录态 | 违反 2026-09-11 的决定，并把服务变成登录态农场 |
| 现在就设计主机与存储层面的访问控制：文件权限、静态加密、运维审计 | 访问控制放在展现层，每次读写都已在接缝处解析为唯一租户；运维层面的冗余等真实需要出现再做（founder，2026-10-26） |
| v1 为每个 planner 任务配一个 microVM 或 gVisor 沙箱 | v1 的 planner 不能运行任何代码或命令（插件已禁用，`toolBash` 关闭），沙箱不会隔离它触达得到的任何东西。它会成为托管的会话式 agent（Q6）和任何多租户云端浏览器的基线；入场条件见 RFC §4.8 |
| 用每租户的提供方 API key 取代 broker 与缓存标签 | 它要求提供方具备该能力，并且得到的控制无法离线测试；broker 与标签在我们自己的边界上测试。以后可以再加上它，而不必拿掉这两者 |

## 6. 待解问题

- 模型提供方是否按 API key 或工作区隔离 prompt 缓存。若是，缓存标签就变得多余，但并无害处。
