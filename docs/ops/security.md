## 1. Reporting a vulnerability

- **Preferred channel**: GitHub Security Advisories on the Danceiny/gotry repository (private disclosure; the maintainer and triage agent are notified without exposing details in public issues).
- **What to include**: a minimal reproducible snippet or commit reference; affected version (use the `npm view @danceiny/gotry versions` output or the corresponding `git rev-parse HEAD`); expected vs actual behavior; impact assessment. Logs, session traces, and screenshots that do not leak private user data are welcome.
- **What to exclude**: real user data (the `gotry-state/` directory under any user's HOME); live credentials for any upstream (FlyAI, hbcli, dida, OpenAI-compatible relays); private alert text from automation scanners that may carry personal data of the reporter. The reporter should sanitize before sharing.

## 2. Triage discipline

The T0-T5 stages in [`external-pr-workflow.md` §1-§6](external-pr-workflow.md) apply to inbound security reports the same way they apply to inbound security PRs. Specifically:

- **T0 source classification** — humans, automation bots (semgrep family, Dependabot, AI-agent generated), and suspected spam each carry a default stance. Bot reports are not treated as ordinary contributions: their conclusions are falsified or confirmed against source code in T2 before any code change is considered.
- **T1 supply-chain precheck (hard gate)** — any diff touching `.github/`, dependency manifests, build/release chain, or introducing new network egress / subprocess execution is an outright veto.
- **T2 claim verification** — security claims are confirmed against source code line by line. Confirmed false-positive patterns recorded in [`external-pr-workflow.md` §3](external-pr-workflow.md) §3 are the standing reference.
- **T3 review and testing** — maintainer-runs the local evidence the external contributor cannot produce. Pure-doc changes substitute N/A + burden-of-proof per the PR template.
- **T4 adjudication** — three outcomes: merge / request changes / close. Adjudication overrides default call when founder rules (e.g. #250 — see §3.1).
- **T5 archival** — disposition lives in the PR comment; this document updates only when a new false-positive pattern or a new precheck rule appears.

## 3. Historical security events (append-only)

This section is append-only; entries are added in reverse chronological order. Each entry records the issue/PR, the claim, the verification outcome, and the adjudication. No edit is made to past entries.

### 3.1 — #250 SQL injection template-literal false-positive (2026-09-08, automated scanner)

- **Source**: external PR by `anupamme`, generated by OrbisAI Security (automation bot).
- **Claim**: `ts/src/state-ledger.ts` `readEvents()` and `deleteEvents()` interpolate dynamic values into SQL via template literals — flagged as `utils.custom.sql-injection-template-literal`.
- **Verification (T2)**: the `readEvents()` interpolation was a compile-time-constant branch selector (`WHERE tenant_id = ? AND kind = ?` vs `WHERE tenant_id = ?`); all dynamic values are bound via `?` placeholders through better-sqlite3 `prepare().all()/run()`. The `deleteEvents()` interpolation was an `IN (${placeholders})` where `placeholders = s.kinds.map(() => '?').join(',')` — the standard parameterized-binding form, which is the precise defense the rule should recommend. Both patterns are recorded in [`external-pr-workflow.md` §3](external-pr-workflow.md) §3 as standing false-positive references.
- **Adjudication (T4)**: founder ruled to merge it as defensive hardening rather than close it (the default call). The change replaced the static branch in `readEvents()` with two explicit `prepare(...).all(...)` calls and rewrote `deleteEvents()`'s placeholder concatenation using `+` string concatenation with a comment-equivalent comment. Both edits are functionally identical to the prior code; the merge records the false-positive disposition in the PR comment and this entry.
- **Status**: merged into `main` on 2026-09-09 via `028ddaa7` ("Merge pull request #250"). The disposition establishes the standing rule for the same scanner pattern against the same target: future occurrences close directly, citing this PR number.
- **Audit trail**: PR #250 (comments), commit `028ddaa`, original commit `700b963`. No CVE was filed (false positive); no security advisory published.

## 4. Disclosed vulnerabilities

The repository has no CVE-filed or security-advisory-disclosed vulnerabilities to date (as of 2026-09-11). Past events recorded in §3 were confirmed false positives or routine dependency upgrades.

## 5. Outbound security responsibilities

- **npm publish 2FA**: every published version is gated by GitHub-side or npm-side 2FA; the founder performs the browser approve at publish time. Granular bypass tokens are explicitly avoided per the documented npm 403/405 behavior ([`tokens.md`](../tokens.md) §2). No published version bypasses this gate.
- **Web Store submission**: the Session Bridge extension's privacy posture is documented in [`extension-privacy.md`](extension-privacy.md). Submission mechanics in [`extension-webstore-submission.md`](extension-webstore-submission.md).
- **External PR workflow**: any security-relevant external PR follows the T0-T5 stages in [`external-pr-workflow.md`](external-pr-workflow.md); no shortcut.
